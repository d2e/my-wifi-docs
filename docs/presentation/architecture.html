One cable decides a lot

What goes with it

Dashboard, whole-home DNS and ad-blocking, every poller — and the internet path for anything behind the hub.

What survives

Both Huawei radios, the gateway, and the hub’s own Wi-Fi clients. The hub is alive, just unreachable.

Step 2 — the radio plan

Four radios that stay out of each other’s way

5 GHz — four non-overlapping channels

2.4 GHz — the classic 1 / 6 / 11 plan

Everything is pinned

No radio is left on auto-select. Channel, width and beamforming are written explicitly to each vendor’s own CLI or web API.

… and re-pinned by itself

A reboot sends the Huawei radios back to auto. The hub spots the (auto) suffix within ~20 s and writes the plan back.

Step 3 — the hub

One router, three jobs

TP-Link Archer A6 · 192.168.0.12 · OpenWrt. Everything runs in ucode, the native OpenWrt engine — no Python, no Node, no container.

🔊 Pollers

Read everything, constantly. Mesh every ~20 s, the TVs every 3 s, the air conditioner every 10 s. They are the only thing that ever touches a device for telemetry.

⚙ APIs

Turn a click into a real command. Four small REST endpoints that log into the access points, drive the TVs, and publish to the AC’s cloud.

📺 Dashboard

One screen for the house. Network, home theatre, climate, downloads — served straight off the router at mesh.html.

Why it matters that these are separate

A web request never waits on a device. The pollers own all device I/O and leave their results in a file; the APIs just read that file. That is the difference between a dashboard that answers in milliseconds and one that hangs for half a minute behind a telnet login.

Step 4 — the heartbeat

One poll cycle, every ~20 seconds

01
Ping the gateway and both access points
02
Sweep the subnet to refresh who is out there
03
Read its own two radios locally
04
JioRouter local storage, Transmission & DLNA audit
05
One visit to AP #2: stats, kicks, USB chores
06
Ask the gateway for its clients and DHCP names
07
Resolve unknown hardware makers, cache forever
08
Fix what drifted: channels, roaming, downloads
09
Write one JSON file — atomically
OUT
That file is the dashboard’s entire data source

The constraint that shapes it

Each Huawei access point accepts one telnet session, ever. Leave one half-open and the next cycle is locked out, so the whole visit is budgeted, batched and torn down cleanly.

Self-healing, not alerting

Drifted channel, stopped download daemon, sticky client on a weak signal — the cycle corrects them and writes a line to a log instead of asking anyone to intervene.

Step 5 — why it feels instant

Nobody waits for a device

It also protects the hardware: a dashboard that opened its own telnet session would collide with the poller and lock the access point out of both.

Step 6 — the home theatre

What we can drive, and what we proved we can’t

  • worksVolume, mute, power, system-audio, picture and sound profiles, one-click scenes Each one verified by watching the actual HDMI-CEC frames on the bus, not by trusting the command’s return code.
  • closedThe soundbar’s own proprietary sound-field commands, and bass / surround trims Four separate routes tested and ruled out. One of them reports success and transmits nothing — which is exactly why we verify against the bus.
Step 7 — the exception

The air conditioner has to go outside

What we get from it anyway

Real energy use per day and per month, straight from the vendor’s own meter data — cached for 15 minutes so the dashboard stays useful when the cloud is not.

What we read locally

Signal strength, link rate and retry rate come from our own radio, not the cloud. The unit sits on the hub’s 2.4 GHz at about −60 dBm.

Step 8 — a bug worth showing

“Deleting files never freed any space”

Fixing the setting was not enough: the download already in flight had cached the old path in its own resume file, and survived both a config change and a restart. The lesson that stuck: when a path fix “doesn’t take”, check what in-flight state cached the old value before you doubt the fix.

What the project taught us

Four rules, each bought with a real outage

  • A write that reports success is not evidence it took effect Settings that read back correctly, APIs returning success, commands exiting zero — all three have lied on this hardware. Verify against the subsystem’s own state, never the setter’s return value.
  • The end state looking right doesn’t mean the mechanism ran A keep-alive sat broken for weeks while its monitor stayed green, because the processes it was supposed to revive happened to already be running.
  • Deploy first, then test Running the suite before copying the file tests the previous copy and passes for the wrong reason.
  • A confident explanation that contradicts the timeline is still wrong An exhaustively evidenced “soundbar firmware defect” was disproved by a reboot — the user had said it worked yesterday, which no permanent defect can explain.
